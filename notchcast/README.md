# Notchcast maintainer guide

**Notchcast** is a modified fork of [Tinycast](https://github.com/abue-ammar/tinycast) (AGPL-3.0; a modified version, as its section 5a requires us to state): upstream `main` plus a few commits of ours on top, arm64 builds signed with our own identity. Upstream's README is at [abue-ammar/tinycast](https://github.com/abue-ammar/tinycast#readme).

Every ~10 minutes a GitHub Actions workflow replays our commits onto the newest upstream `main`, builds and runs the tests, and moves `main` only when green; each upstream release is rebuilt the same way and published here under the same tag.

This file is `notchcast/README.md`, the maintainer guide. The public root `README.md` is generated from `notchcast/README.public.md`; its feature list sits between the `features:start` and `features:end` markers, and `CHANGELOG.md` (Keep a Changelog) records user-visible changes per release. `main` is the default branch. Feature work happens on branches off `main` and lands as linear commits (no merge commits). Features are our own code; Notchcast uses no Raycast extensions.

Our commits:

- `Notchcast: read releases from kaczordodgers/notchcast`: the in-app updater reads this repo's releases.
- `Notchcast: remove upstream workflows`: none of upstream's workflows run here. The sync makes this commit afresh on every replay, so upstream workflow edits never conflict and new ones never land.
- `Notchcast: let a LaunchAgent own starting the app`: with `NOTCHCAST_LAUNCHD=1` the app keeps its login item off and its Relaunch only quits, so the LaunchAgent below is the only thing that starts it.
- `Notchcast: tooling` and later fixes: this folder and `.github/workflows/`.
- `Notchcast: bundle id app.notchcast, URL scheme notchcast, name Notchcast`: our own app identity (Debug: `app.notchcast.dev`). The in-app updater treats it as a development build and stays inert; `notchcast.update` installs releases.
- `Notchcast: generated files`, always last: the root `README.md` (from `notchcast/README.public.md`), `Tinycast.xcodeproj` (XcodeGen from `project.yml`) and, when our commits change `Scripts/raycast-runtime/`, `Tinycast/Resources/RaycastRuntime.generated.js`. The sync makes it afresh; our other commits never carry these files (replay drops them from each commit), so upstream edits to them never conflict. It also removes every path in `notchcast/prune-paths.txt` (upstream files the app does not need, e.g. `website/`), so upstream edits to them never conflict either. Edit `notchcast/README.public.md` or `project.yml`, never the generated files.

## Sync (`.github/workflows/sync.yml`)

- Rebase waits while a non-draft PR from this repo into `main` is open, for at most 12 hours from the oldest upstream commit not in `main`, then proceeds with a warning.
- A replay whose `main` lease is lost because `main` moved meanwhile (a landing or the generated-files push) ends green with a notice; the next Sync (that push, or kick within the hour) replays again.
- Started by `notchcast.kick` (below) when upstream `main` or its newest release changed, at least hourly, on a push to `main` except generated-only changes (`Tinycast.xcodeproj/project.pbxproj`, `Tinycast.xcodeproj/xcshareddata/xcschemes/Tinycast.xcscheme`, `Tinycast/Resources/RaycastRuntime.generated.js`, `README.md`), and by hand. GitHub's own `schedule` stays in the workflow but has never fired for this fork. Each run: if upstream `main` moved, the plan job first replays our commits on Linux; a conflict is reported there without spending a macOS runner. Then `notchcast/ci.py replay` cherry-picks our commits (`merge-base(main, upstream/main)..main`) onto the new upstream `main`, builds Debug on a GitHub-hosted `xcode-27` runner and runs upstream's `Scripts/run-tests.sh`. Only when green does it update `main` with `--force-with-lease` on the `main` it started from. That workflow push is the only history rewrite allowed in this repo; nobody force-pushes by hand. A `main` commit without a green `notchcast/tested` status (a push) is built and tested as it is, and gets that status when green; unless a green PR build of this repository already built and tested its tree: after a green build the PR workflow uploads a `tested-tree-<tree>` artifact (the tree of the checked-out commit without the project, scheme and `README.md`, which CI regenerates or never tests; the Raycast runtime stays in, `ci.py tested-key`), and plan marks `main` tested from a live one whose run is a green `pr.yml` run of `FORK_REPO` (fork PRs never count) and closes the `notchcast-main` issue. Any miss or API error tests `main` as before.
- Every upstream release from `BASELINE_TAG` (`config.env`) on is rebuilt from its tag with our commits replayed onto it, tested, built Release for arm64, signed with `Notchcast Self-Signed` and published under the same tag, title and prerelease flag as `Notchcast-<version>.zip` and `.dmg`. Version and build number come from upstream's own zip; mirror versions stay unchanged; snapshots append a numeric revision. Upstream's tag is mirrored unchanged.
- Tests: upstream's full suite except `CI_SKIP_TESTS` (`config.env`), harnesses the hosted VM cannot run (Vision OCR, rendered-text capture), which must still pass on a Mac. A harness that fails is run once more alone; if it still fails, it is run on the pristine upstream commit under our commits, and only a harness that passes there blocks (a failure on upstream too is upstream's flake or the VM, and is ignored with a warning).
- On a replay conflict, a red build or a red test nothing is pushed or published and `main` stays as it is. Land a hand resolution as `notchcast/replay-fixes/<name>.patch` (full diffs covering exactly the conflicting non-catalog, non-generated files, from the replay's current tip to resolved content; clean cherry-pick results are preserved; lowercase subject with non-alphanumeric runs replaced by hyphens, trimmed at both ends); delete it once Sync has rewritten main. When an older release tag needs a different resolution, add it as `<name>.<base label>.patch` (e.g. `<name>.v0-12-9-beta-134.patch`): the replay tries `<name>.patch` first, then the labelled ones in name order, and uses the first that applies; delete a labelled one once its release is published. A red build or test is remembered as `refs/notchcast-failed/<main-<upstream>|release-<tag>|test>-<main>`, so it is retried only when upstream or `main` changes; a conflict is found again cheaply on Linux each run.
- Each failure opens or updates one issue per kind, closed by the next green run of that kind: `notchcast-sync` (replaying onto new upstream), `notchcast-main` (a pushed `main` tested as it is), `notchcast-release` (per tag). A conflict's issue names our commit and files and lists the upstream commits that touched them. A cause that stays the same (the same conflict, the same red `main`, the same tag) on a newer upstream only retitles the issue. On a maintainer machine with a notify hook (see [Private hooks](#private-hooks)), the updater reports each issue and cause once.
- A sync that brings upstream changes under `Tinycast/DesignSystem/`, to `Theme.swift` or to `docs/ui.md` opens one `notchcast-design` issue listing those upstream commits. On a maintainer machine with a task hook, the updater turns it into one private task, "Refresh notchcast/docs/design-system.md", and closes the issue.

## Shared repository configuration

`notchcast/config.env` owns the repository names, maintainer identity and tested-status context. Shell scripts source it. Python tools use `ci.config()`. Git URLs and the trusted local-status creator are derived from those values.

`python3 notchcast/check-config.py` compares literal counts in `notchcast/` and explicit lists of fork-owned workflows and GitHub documents with `notchcast/config-literals.json`. Upstream-owned files are never scanned, and the guard runs during build checks, not before replay planning. The checked exceptions are documentation and historical source references, independent test fixtures and workflow comments. `python3 notchcast/check-config.py --list` lists every path and key. A changed literal or an unlisted copy fails. `python3 notchcast/check-config-test.py` demonstrates a deliberately wrong literal failing and the restored literal passing.

Snapshot and Sync both use `notchcast/actions/release` for signing, Release arm64 compilation, signature and identity checks, a 30-second launch check, and zip and dmg packaging. The action receives version, build and signing material explicitly. Identity is checked after signature verification in both workflows. Publication and cleanup remain with each workflow. `bash notchcast/release-test.sh` checks that both workflows call the action once and exercises live and crashed process fixtures. The test uses Ruby's standard-library YAML parser.

## Secrets and checks

- Actions secrets live in the environment `sync`, which only `main` may use: `SIGNING_P12_BASE64` and `SIGNING_P12_PASSWORD` (the self-signed code-signing identity) and `DEPLOY_KEY` (write deploy key `notchcast-actions`; `GITHUB_TOKEN` cannot push commits that touch workflow files). The same material is kept outside git on the maintainer's Mac. The public leaf fingerprint is `SIGN_SHA1` in `config.env`.
- `.github/workflows/leaks.yml` and the hooks in `notchcast/githooks` run gitleaks and `check-identity.sh` (no employer name in files, commit messages or commit identities). Per clone, before the first commit: `git config core.hooksPath notchcast/githooks`, a repo-local `user.email` noreply address, and `git remote set-url --push upstream DISABLED`.
- Sync commits use `github-actions[bot]`; snapshot annotated tags use the repository identity.
- UI checks: `notchcast/design-check.sh` runs [enmerasoftware/ai-design-check](https://github.com/enmerasoftware/ai-design-check) (version `DESIGN_CHECK_VERSION` in `config.env`; Node 20+) on `Tinycast/` with upstream's own findings as the baseline, so only what our commits add counts: errors fail (icon-only buttons without a name, Title Case text, radii and type off the scale, ...), warnings are shown. It runs in `.github/workflows/design.yml` on pushes and pull requests that change Swift, and in the pre-commit hook when Swift under `Tinycast/` is staged. A deliberate exception gets `// ai-design-check-ignore-next-line <rule> -- <reason>`.

## Private hooks

Maintainer-specific integrations stay out of this repo. `kick.sh`, `update.sh` and `local-ci.sh` source `~/.config/notchcast/private.env` when it exists; every hook is optional, and a missing one turns its feature off:

- `notchcast_notify`: a shell function that receives one alert line on stdin (sync trigger failures and open failure issues).
- `notchcast_task <title> <description>`: files a private task for a `notchcast-design` issue and prints its id; the issue is then closed. The drift reporter also calls this hook once per threshold crossing. It loads the same private file, prints `no task hook` when the function is absent, and never stores private task ids in git.
- `notchcast_build_done`: receives the `build/local` result line on stdin when `local-ci.sh` ends.
- `NOTCHCAST_BUILD_QUEUE`: a command that runs `hold [--landing] -- <command>` through a machine-wide build queue (`local-ci.sh`, and `app-proof.py` from the environment). Without it, builds run directly.
- `NOTCHCAST_LOCAL_CI_DIR`: where `local-ci.sh` keeps its logs (default `~/Library/Caches/notchcast/local-ci`). The build scratch always lives in the per-user temporary directory (`getconf DARWIN_USER_TEMP_DIR`): Debug binaries embed absolute source paths that `-file-prefix-map` does not remap (Swift's escaping-closure check), so a tree under the home would put the user name into the bundle and fail the identity step.
- `NOTCHCAST_AGENT_SESSIONS_EXCLUDE`: comma-separated path-component prefixes that Agent Session Logs must never access, matched case-insensitively. The app reads this key as plain `KEY=value` text from `~/.config/notchcast/private.env` on each refresh and never executes the file. A missing file or key excludes nothing; an unreadable or invalid UTF-8 file, more than one line naming the key, or a line that is not one `[export ]KEY=value [# comment]` assignment whose value, bare or in one pair of `"` or `'`, uses only `A-Z a-z 0-9 - _ . ,`, prevents the scan. Any line holding the key's letters in order counts as naming it. The app sees the key only when it is written out literally on one line of this file; a value set by another sourced file or an `eval`, or under a key name the shell builds (a variable, `$'\…'` escapes, `$(…)` or brace ranges), is not seen, so write the key plainly and only here.

## Installing on a Mac

`notchcast/install-launchd.sh all` once per Mac; logs are in `~/Library/Logs/notchcast/`. It:

1. installs the newest snapshot at `/Applications/Notchcast.app` (`update.sh`);
2. copies the old Tinycast Beta data once (`migrate.sh`), each part only while the Notchcast side is still empty: preferences (`defaults export com.tinycast.app.beta | defaults import app.notchcast`), `~/Library/Application Support/com.tinycast.app.beta/` and `~/.config/tinycast-beta/settings.json` (to `~/.config/app.notchcast/`). The old data is never changed. Keychain secrets (keyed by bundle id) are not copied;
3. quits Tinycast Beta and moves its `.app` to the Trash;
4. loads the three LaunchAgents:
   - `notchcast.app` runs `/Applications/Notchcast.app` itself: started at login, restarted after a crash or a Quit (`KeepAlive`, at most every 10 s), with `NOTCHCAST_LAUNCHD=1`. Stop: `launchctl bootout gui/$(id -u)/notchcast.app`. Start: `launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/notchcast.app.plist`.
   - `notchcast.kick` runs `kick.sh` every 10 minutes (needs `gh` logged in; `install-launchd.sh kick`): it starts `sync.yml` when upstream `main` or upstream's newest release differs from what it last started for, and at least hourly. If a Sync is queued, pending or waiting, it logs a skip (also with `--dry-run`) and leaves trigger state for the next tick to re-evaluate. With a notify hook it reports once when it cannot start the sync, and once per upstream commit missing from our `main` 40 minutes after it was committed while no `notchcast-sync` issue is open. Log: `~/Library/Logs/notchcast/kick.log`.
   - `notchcast.update` runs `update.sh` every 30 minutes (needs `gh` logged in), unless Notchcast's own "Automatically check for updates" is off (`general.automaticallyCheckForUpdates: false` in `~/.config/app.notchcast/settings.json`; then it logs that and installs nothing): the newest snapshot is installed when its timestamp is newer, the installed version is not a snapshot, or the timestamps match and the installed copy is not ours, after checking bundle id, version and our leaf certificate. A release that failed its check is not installed again until `update.sh --retry`. `install-app.sh` keeps one previous bundle in `~/Library/Application Support/notchcast/previous/`, sending its predecessor to the Trash. It kickstarts `notchcast.app` and watches its pid and run count for 60 seconds, restoring and watching the previous bundle if the new one fails. Failed bundles go to the Trash. An unloaded agent skips the check; every install logs what was left running. `notchcast/update.sh --install` bypasses only that preference, for example to install a build on every maintainer machine at once; combine with `--dry-run` in either order to check without installing. Settings, data and Keychain items are never touched.

The new bundle id and signature need Accessibility to be granted once.

Before each update run, the job fetches origin `main` and runs its `notchcast/` tooling from `~/Library/Application Support/notchcast/tools`, leaving the checkout untouched; if refresh fails, it logs and uses the last extracted copy or the checkout. After a change to the job wrapper, run `notchcast/install-launchd.sh update` once on each installed Mac to rewrite it. A newer snapshot (automatic or `--install`) installs and restarts the app at once; there is no idle wait.

## Conflict-free PRs

Merge only with `notchcast/land.sh <pr>`. It checks an isolated merge of the PR head into current main, runs core and affected fork harnesses, and squash-merges only that PR head after they pass. It refuses unless the PR targets `main`, `build` is green on that head, and `design` and `leaks` passed on it when they ran (path filters may skip them). A PR cut before a Sync rewrite merges from its fork point on the replaced main, which Sync keeps under `refs/notchcast/synced/`. It always runs main's copy of `notchcast/`, and it, like the generated-files push, waits while a Sync plan or replay holds the main lease. Main harnesses runs only on manual dispatch (`notchcast-ci.py` branch proofs), not on pushes to main, where Sync's `test_main` runs the full suite on the same commit; it selects the harnesses changed since `notchcast/fork-point.sh origin/main HEAD`, in one parallel invocation with retries alone and upstream failure comparison, with a 30-minute timeout. This is not an app build: switches in files no selected harness compiles, UI integration, and main moving between the check and the merge remain outside its protection; the PR build is still required. The PR workflow does not build draft PRs (converting to draft cancels a running build; `land.sh` refuses a skipped build); mark the PR ready, or dispatch it, to get one.

`notchcast/local-ci.sh <pr>` builds and tests the exact PR head on a maintainer machine, through the build queue when one is configured. Before the build it runs land.sh's drift gates (`notchcast/drift-gates.sh`) on the merged tree, so a drift refusal fails local CI with the same `REFUSED:` message. It posts `build/local` success or failure with the minutes and the last step, and keeps the log in `$NOTCHCAST_LOCAL_CI_DIR/logs/<sha>.log`. Success cancels that head's pending PR Actions runs and supplies build proof to `notchcast/land.sh`.

One landing hold covers every Mac: `notchcast/hold.sh set <owner> <minutes>` (owner: a PR number, or a name the lander passes as `NOTCHCAST_LAND_AS`), `hold.sh show`, `hold.sh release`. It is the repository variable `LANDING_HOLD`; until it expires, `land.sh` lands only the owner's PR, checking at its start and again before each push, and refuses when the hold cannot be read. Meanwhile the owner's `local-ci.sh` build takes the build queue's landing lane, ahead of every normal job, and any other PR's `local-ci.sh` waits until the hold ends.

PRs carry no generated files: edit their inputs, regenerate locally before using Xcode (`xcodegen generate`), and leave the generated diff uncommitted. PR CI regenerates before building. After each source push to main, the Generated files workflow runs `ci.py regenerate` and commits only `GENERATED` as `Notchcast: generated files` with the repository identity; each attempt starts from a fresh `origin/main`, its generated-only push is excluded by path filters, and the Actions token starts no further workflow runs. If it waits out a Sync replay past its 60 min timeout and that replay fails, main keeps stale generated files until the next source push. Sync regenerates before every build too.

Fork harnesses are discovered by `notchcast/test-harnesses.sh`, so a PR never edits `Scripts/run-tests.sh`. `notchcast/harness_inputs.py` resolves inputs for that runner, `changed-harnesses.sh`, and `check-module-harness.py`. `Tests/nc-<Folder>-<name>-test.swift` compiles all Model and Service sources of `Tinycast/Features/<Folder>/`. A `// notchcast-sources: <compiler arguments and source globs>` or `// notchcast-kit:` header overrides that folder rule. Other fork harnesses (`Tests/notchcast-*-test.swift` or an upstream-style name) declare their sources in one or more such lines. Paths contain no spaces. For upstream-registered harnesses it also reads the `run` arguments from `Scripts/run-tests.sh`, resolving its variables and continued lines without duplicating those source lists. The resolver includes conditional additions from `command-harness-sources.sh` in one Bash invocation; registration appends only inputs not already supplied by the upstream `run` line. A resolver failure (including malformed headers or a failing conditional helper) emits `::error::` and terminates the runner rather than passing an incomplete suite. A `notchcast-*` harness without the header fails alone with an error; the rest of the suite still runs, and so does a fork-added upstream-style harness (absent from the upstream merge base) that loses its header (a `// notchcast-reads:` line alone does not count). The resolver fetches a missing `upstream/main` ref from `UPSTREAM_REPO` in `config.env` to tell which harnesses are fork-added, and a failed fetch is a resolver error; outside a git repository (a `git archive` copy, as `notchcast-precompile.py` uses) the fork-added check is skipped. A `// notchcast-kit: <name> [<name>...]` header expands to the globs and compiler arguments listed one per line, `#` comments allowed, in `Tests/Kit/<name>.kit` (`platform`, `input`, `root`), so harnesses name a shared source set instead of copying its file list; an unknown or empty kit is a resolver error, and changing a kit file selects every harness that uses it.

A `// notchcast-reads: <globs>` header declares repository files a harness reads as text or compiles in a child process. Multiple lines are combined. For example, `// notchcast-reads: notchcast/root/*.swift` makes helper changes select the harness without adding helper sources to its own compiler arguments. Selection matches the patterns against changed paths, including deleted files. Recursive read sets use `**`, for example `Tinycast/Features/**/*.swift`. Capture harness read declarations remain pending for `Tests/*Capture*`, `*ColorPicker*`, `*Recording*`, `*Scrolling*`, and `*Trimmer*`.

`notchcast/ci-build.sh` runs `python3 notchcast/script-tests.py`, which recursively discovers `notchcast/**/*-test.py`, `*-test.sh`, `*-test.mjs` and `*-test.swift`, including tests directly in `notchcast/`. They run with Python, Bash, Node and Swift 6 respectively. The default PR/local-CI lane excludes three explicitly listed tests: `land-test.sh` (slow merged-tree harness runs), `install-app-test.sh` (starts a launchd agent and leaves installation scratch), and `gallery/keychain-test.py` (queries the host Keychain). Run `python3 notchcast/script-tests.py --all` only on a machine where those effects are intended. Pass `--list` for the default paths or `--all --list` for every discovered path. Run it from the repository root; finding no tests is an error.

## Drift gates

`python3 notchcast/check-drift.py` checks fork-owned Swift against `notchcast/drift-baseline.json`. It scans production sources under `Tinycast/` and `notchcast/root/`, counting each repository path once even when the root helper compiles a Tinycast source. Ownership comes from files added since the merge base of `HEAD` and `upstream/main`, including working-tree additions. The checker fetches the upstream ref from `UPSTREAM_REPO` in `config.env` only when that ref is missing. Upstream-owned Swift is read for references but never gets a gate budget.

The baseline maps each rule to stable keys and integer counts. Each key occupies one line to reduce overlap, but reductions to adjacent keys can still conflict. Keep retired keys at zero instead of deleting them; `--write-baseline` preserves them. A new finding or a higher count fails. A lower count also fails with `lower it in drift-baseline.json`, so removing debt requires lowering its budget in the same change. `--write-baseline` seeds the initial file or tightens existing counts, but refuses growth. `--compare-base <commit>` rejects every added or raised entry, including alert thresholds and zero-valued new keys; a `path` or `path:name` key whose file git pairs as a rename (`-M`) is compared under its old path, while clone and boundary keys are not followed, so a move that changes them still reads as growth. A base without the file permits its first installation.

| Gate | Rule and key |
| --- | --- |
| 1 | Feature-to-feature lexical type references are counted by folder pair. A feature may use its own types, upstream types, `Platform/`, and the reviewed `KERNEL` set in the checker. `NotchcastCore.<member>` lookups outside the kernel are counted per file. Fork files inside upstream feature folders are counted per file. |
| 2 | Production files over 400 lines and fork harnesses over 600 lines are counted by path and exact line count. `Tinycast/Features/Notchcast/Core/NotchcastFeature.swift` is exempt because its registry grows by one line per feature until Phase 2b removes it. The planned harness limit is 400 at phase 5. |
| 3 | Types and top-level or static/class members with no production use are counted as `path:symbol`. A name found only in tests gets a separate `test-only` budget. Indented instance functions and properties are skipped to avoid treating SDK callbacks as dead code. Overrides, Objective-C entry points, `@main`, and property wrappers are exempt. The check is lexical, not a compiler reachability proof. Reused names can hide findings. |
| 4 | `npx -y jscpd@$JSCPD_VERSION` checks a temporary copy of fork production Swift for clones of at least 70 tokens and 6 lines between different files. The key is an unordered file pair, and the count is its clone count. The exact jscpd 4 version is pinned in `config.env`. Missing npx, a failed invocation, a 120-second timeout, or a missing or malformed report fails closed. Lowercase literals beginning with `app.notchcast`, `notchcast.`, `com.notchcast`, or the preference-domain prefix `com.apple.` are counted by literal and number of owning folders. Icon names and standard protocol strings are outside that scope. The planned clone threshold is 50 tokens at phase 6. |
| 5 | `--report` prints each gate against its baseline, near-limit files, waivers, dead and test-only symbols, pattern counters, added lines in modified upstream files except generated outputs, and landed fix commits carrying `No test:`. The reporter never runs an indexed build. |

A line ending in `// drift: keep <reason>` exempts that line. A file-size exception uses that marker on the final line. Empty reasons do not waive anything. Reports count these exceptions. Boundary checks reuse `notchcast/bin/swiftgraph.py` and its literal stripper and file graph. The checker disables Python bytecode writes.

`land.sh` refreshes `upstream/main` before merging so upstream additions are not charged to the fork. It runs the baseline comparison and all four gates immediately after the feature-shape check on each merged candidate, including retries after main moves. The gate checker and its imported graph code come from the landing base, not the candidate; the first installation uses the invoking checkout when the base has no checker. Tests cannot prove a gate change safe, so a change to `notchcast/check-drift*`, `notchcast/bin/swiftgraph.py`, `notchcast/config.env`, `notchcast/land.sh` or the files it sources (`hold.sh`, `sync-wait.sh`, `local-build-status.sh`, `drift-gates.sh`) is a visible sign-off: landing refuses unless the PR body has a line `Drift tooling: <reason>`, and that line is kept in the squash commit. For the drift tooling itself, the landing base's `check-drift-test.py` also runs against the merged tree with `python3 -I`, as a sanity check only, and a PR that deletes that file is refused. A budget increase refuses with `REFUSED: drift baseline grew`. Other drift failures re-run the checker on the base, print `main is already red` when that also fails, and refuse with `REFUSED: drift` either way. The pre-push hook runs gates 1 to 3 without npx and warns rather than blocking. `land.sh` and `local-ci.sh` share these gates through `drift-gates.sh`; they run locally, not in `ci-build.sh` or an Actions workflow.

A PR whose title starts with `Fix ` after removing an optional `Notchcast: ` prefix, case-insensitively, must add or change a `Tests/*-test.swift` or `notchcast/**/*-test.*` file. Otherwise landing refuses unless the PR body has a line `No test: <reason>` with a nonempty reason. That line is retained in the squash commit for the report counter. This is the cheap presence check only. It does not prove that the changed test failed on the base commit.

A run of all four gates, which is what `land.sh` and `local-ci.sh` do, ends with the counters (each rule's total against its baseline total, and the alert counters), so the log shows how close each limit is. Each key above its limit prints one machine-readable line, `GATE-THRESHOLD <rule>:<key> <value> <limit>`, such as `dead:<path>:<symbol>`, `clones:<path>|<path>` or `file-lines:<path>`; a whole-tree alert counter drops the `:<key>`. In a gate run, an alert crossing whose value does not exceed what the merge base with `origin/main` already had ends with `known`, so only lines without it are new; the post-landing `--report` marks none. The pre-push subset (gates 1 to 3) prints none of this. A reviewer gets only the goal and the diff ([docs/review.md](docs/review.md)).

After a successful landing push, PR close, and branch cleanup, `land.sh` reports the landed commit. Report failures warn but do not undo or block the landing. Each alert threshold is in the baseline's `alerts` map. A production file at 350 lines or a harness at 550 lines crosses its near-limit threshold. Other counters alert above their seeded counts. The optional task hook receives a title and a description containing the counter, value, threshold, and key. Crossing state is locked and atomically saved by counter and key in `~/Library/Caches/notchcast/drift-alerts.json`. The first report, before that file exists, records counters already above their thresholds without filing tasks; when the file is missing, `land.sh` first runs that report on the landing base, so a crossing the landed commit adds is still filed. A repeated report above the same threshold creates no new task. Falling below it rearms that key. An absent or failing hook leaves the crossing unacknowledged for a later retry. Hook fixtures use an isolated `HOME` and a stub hook.

`python3 notchcast/check-drift-test.py` plants boundary lookups, oversized files, dead and test-only declarations, generated clone blocks including one at exactly the jscpd limits (70 tokens, 6 lines), root-helper violations, and copied fork/preference literals. Each deliberate violation must exit 1 at its gate. It also checks waivers, SF Symbol exemptions, fail-closed clone checking, baseline tightening, and stub-hook calls: none on the first report, one on a new crossing, none on rerun. `python3 notchcast/land-drift-test.py` exercises the actual landing budget comparison, defect-test presence rule, `Drift tooling:` sign-off, base-fixture run, first-report seeding, and non-blocking report. The older merged-tree harness fixtures isolate these gates because the drift fixtures test them separately.

## Snapshot releases

`.github/workflows/snapshot.yml` starts primarily on pushes to main, with a cron backstop at minutes 7, 27 and 47, and by manual dispatch. Workflow-level concurrency holds the `snapshot` group through planning, building and publishing, with `cancel-in-progress: false`. Automatic runs wait on Ubuntu until 50 minutes after the latest published snapshot's tag timestamp, then refresh main and releases; unchanged main skips. macOS only receives a planned build pinned to that refreshed main. Manual dispatch never waits in the planner: unchanged main fails with an error; a closed gate exits successfully with a notice including its UTC opening time. A dispatch can still be cancelled while pending when a newer run replaces it: it ends grey "cancelled", never green, and the replacing run builds current main. Sync's deploy-key and land.sh's authenticated pushes trigger Snapshot; Generated uses GITHUB_TOKEN, so its pushes rely on the backstop. The intended build start is within about 15 minutes of the gate opening, subject to GitHub scheduling and runner availability. Failed attempts do not block retries. Snapshot planning tests run only in this workflow, before planning.

To publish a waited-for fix early, first cancel any Snapshot run still waiting in `plan` (it holds the `snapshot` group; cancelling it there publishes nothing): `gh run list -R kaczordodgers/notchcast -w Snapshot -s in_progress`, then `gh run cancel <id> -R kaczordodgers/notchcast`; then `gh workflow run Snapshot -f skip_gate=true -R kaczordodgers/notchcast`. It bypasses only the 50-minute gate, retaining unchanged-main protection and every test, lint, signature, identity and launch check.

Generated files retries runner allocation at most twice when its sole `regenerate` job was cancelled before any step started and has GitHub's hosted-runner not-acquired annotation; script failures and exhausted allocation failures remain red.

The workflow regenerates the project and uses sync's `notchcast/actions/tests` action on the captured main commit, including hosted-runner exclusions, retries and comparison against pristine `merge-base(main, upstream/main)`; it skips that action when the main commit already has a green `TESTED_CONTEXT` status from Sync. Lint must also pass. Either failing fails the snapshot without publication; Leaks is independent. Green commits use sync's Release arm64 build, signing identity, signature checks and zip/dmg packaging steps. Build or signing failures publish nothing. Snapshot tags point to that exact main commit and use the repository identity.

Tags append `.snapshot.YYYYMMDDHHMMSS` (UTC) to the newest published upstream mirror version, for example `v0.12.7-beta.131.snapshot.20261104120000`. The app version and asset names include the suffix. The updater selects only non-draft releases whose tags end in `.snapshot.` followed by exactly 14 digits, ordered by that timestamp alone. It ignores upstream mirror, beta and stable releases, regardless of their version or publication time. An installed non-snapshot version is replaced by the newest snapshot. An installed snapshot with a later timestamp is kept, and one with the same timestamp is kept when signed by us. Sync's mirror parser ignores snapshot tags. Existing updater copies must be refreshed to use timestamp-only ordering. Updater selection checks run with `bash notchcast/update-install-test.sh`. Snapshot planning checks run with `python3 notchcast/snapshot-test.py`.

Enable independent 30-minute installs on an installed Mac from its checkout with `/bin/bash notchcast/install-launchd.sh update --auto-install`. This reloads only `notchcast.update`, with `update.sh --install` in its arguments, and runs at load and every 1800 seconds. It never changes `general.automaticallyCheckForUpdates`. Run `install-launchd.sh update` to restore preference-respecting behavior. First-time setup can use `install-launchd.sh all --auto-install`.
