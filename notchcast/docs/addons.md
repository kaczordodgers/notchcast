# Notchcast add-ons: the contract

Every Notchcast feature on top of Tinycast is an add-on. An add-on plugs in with one line and comes out with one line, and syncing with upstream stays a non-event. This page says what an add-on may touch, what the core does for it, and how each promise is checked. It replaces v1's `feature-descriptors.md`, `command-hook.md` and `switch-paths.md`.

## 1. What an add-on is

- **Built fresh, never ported.** No feature copies or ports code from v1 (branch `v1/final`) or any local pre-v2 branch; each is written on the island base, with outside projects (Aural, Vorssaint, RemoveMacAI, Peel and the like) as references, credited in the add-on's own `notchcast/licenses/borrowed/<Folder>.txt` when code is taken.
- **One folder:** `Tinycast/Features/Notchcast/<Folder>/`. The folder holds every source the add-on needs. It may hold `Model/` (no AppKit or SwiftUI; every environment fact injected), `Service/`, `UI/` and `Settings/`, plus its own string catalog `<Folder>.xcstrings` (table `Notchcast<Folder>`, English only). A catalog key that names a chord (⌘X, ⌥↩, Hyper) needs that chord declared at column 0 of a file in the folder as `// notchcast-system-keys: <chord> [<chord>...]`, kept for a fixed key the feature itself handles; `notchcast/check-fork-strings.py` fails otherwise, and the core `Notchcast.xcstrings` may name none.
- **It declares itself in its own file**, never in a shared list, so two add-on PRs never edit one line. At column 0 of `<Folder>Addon.swift`: `// notchcast-addon-order: <n>` places it in the registry (take `python3 notchcast/addons.py next`; a tie goes by type name), and optional `// notchcast-readme: <Tab>: <phrase>` lines put it on that tab's line of the README's add-on list (joined by ", ", or by a space after a phrase ending in "," or ";"). `notchcast/addons.py` generates `Tinycast/Features/Notchcast/NotchcastRegistry.swift` from those lines on every `xcodegen generate` (project.yml's `preGenCommand`) and the README's list from `notchcast/README.public.md`; main's Generated workflow commits both, so an add-on PR commits neither. Code it borrows is listed in its own `notchcast/licenses/borrowed/<Folder>.txt`. A harness of its own that runs only on a hosted runner, also on Linux, or never on the hosted VM says so by a column-0 line in that harness, `// notchcast-hosted-only`, `// notchcast-linux-ok` or `// notchcast-ci-skip`, which `notchcast/harness-tags.sh` adds to `HOSTED_ONLY_TESTS`, `LINUX_OK_TESTS` or `CI_SKIP_TESTS`; `config.env` names only upstream harnesses. `notchcast/check-addons.py` fails a branch that edits the registry, writes an entry into `borrowed.md`, puts a phrase on a README tab line or names a fork harness in a `config.env` harness list.
- **Its harnesses** live at `Tests/nc-<Folder>-*.swift`. `notchcast/harness_inputs.py` finds them by their header, so there is no list to edit. An add-on never edits a core harness (`Tests/nc-Notchcast-*.swift`): what the core checks per add-on, it finds by reading the folder and its own harnesses, so the delete test leaves every core harness compiling.
- **Several switches in one folder** are allowed when they share code: Downloads + aria2 + Distill + Timestamps + Torrents + Wi-Fi and iPhone bonding ([downloads-bonding.md](downloads-bonding.md)), Brightness + Volume (one media-key policy). They are then added and deleted together. Two folders never share code; if both need something, it moves into Core as a service with a reason. `Core/Model/NotchcastLinkCleaner.swift` is one: Copy Path and Clean Copied Links strip the same tracking parameters, so the list has one owner.
- **Nothing else.** An add-on edits no upstream file, no other add-on, no Core file, no shared list, no `Localizable.xcstrings` and no generated file (`Tinycast.xcodeproj` is regenerated by CI and never committed).

## 2. What the descriptor declares (the core does the wiring)

`<Folder>Addon` conforms to `NotchcastAddon` and states, as plain data:

- `switches`: one per user-facing feature: frozen string id (the v1 raw value where one exists; an id v1 never had is declared in the folder, at column 0 of any of its files, as `// notchcast-new-switch-ids: <id> [<id>...]`), title, subtitle, `category`, `defaultEnabled` false unless v1 shipped it on, `dependencies` (switch ids, may name another folder's switch: the core then turns it off when that folder is gone), `requiredGrants`.
- `commands`: launcher commands, each with id `command:nc-<slug>` (frozen), name, symbol, owning switch, `run`. They appear as ordinary launcher entries of the existing `AppEntry.Kind.command`, owned by the Notchcast tab holding their switch (`settingsOwner: .notchcast(<pane>)`), so there is no new launcher section and no category guessed from an id; their icon is a tile of their symbol in that tab's tint, set as the entry's `iconOverride` because upstream draws a `.command` only from `CommandID`, and proven by the add-on's own icon harness (§5); the stock Commands category neither lists nor gates them, and their alias and hotkey fields sit under their switch. Commands made from the user's own rows (Script commands) are published at run time by the module with `context.setCommands(_:)`: same id shape, launcher entry and hotkey as declared ones, gone when the module stops; their alias, hotkey and launcher fields sit in the add-on's own settings rows, since the core's rows list declared commands only. `NotchcastContext` is `@Observable`, so such a row sees the module attach. A command may also declare one `argument` (`NotchcastArgument`: a field title and a `run` handed the text): the launcher then shows one inline field beside its row, built like upstream's custom-command fields, and Return hands the typed text to that `run`; an empty field, a hotkey or any other run calls the plain `run`.
- `context.handleLauncherShown(_:)` runs each time the launcher opens, so a module can refresh the commands it published with `setCommands(_:)` (Taildrop's one per device). Their slugs are built from stable facts, never a counter, since aliases and hotkeys are stored under them.
- `hotKeys`: commands may be bound like any built-in command, stored at `hotkey.command:nc-<slug>`, the same key v1 used, so existing `nc-screenshot-area` and `nc-screenshot-display` bindings resolve unchanged. No add-on ships a shortcut of its own or names one in its text: the user records it in the command's field.
- `settings`: extra rows under each switch, written as SwiftUI views inside the folder; the core renders them in the add-on's category section of its tab.
- `taps`: event-tap subscriptions (event mask plus handler). The core installs one shared tap only while at least one enabled switch subscribes, and removes it when the last unsubscribes. Subscribed does not mean live: an add-on that acts outside its handlers checks `context.isTapLive`, and each tap's `reset` runs when the tap drops on its own.
- `makeModule(context)`: start and stop. The core builds the module when the switch and its dependencies are on and stops it when they go off. `context` is the only door to the app: preferences store, presentation seam (island), tap hub, launcher hooks, clock and the doors in [doors/](doors/), one page per door. An add-on never reads `AppCore`, `NotchcastCore` statics or another add-on.
- `context.setUnavailable(entryIDs)`: a running module names the commands it cannot run right now (Noise Control: modes the connected headset lacks); the launcher drops them and their hotkeys still run, so a press reports why. Stopping the module clears it.
- `makeRecovery(context)`: optional, default `nil`. Built and started at core start whatever the switches say, before any module, and stopped at core stop after the modules. It repairs what a previous run left behind (a dirty journal) with the add-on off, so it stays short. It gets its own context, so switching the add-on off and on leaves its tap subscriptions in place; they still install only while their switch is on, and core stop clears them. A module reaches its own add-on's recovery with `context.recovery(RecoveryType.self)` (nil before core start, after core stop, or when the add-on has none), so work it hands over, such as a pending restore, survives the switch going off. A URL or file opened with the app goes to the add-ons' `context.handleOpenURL` claimers, every running module first, then every recovery, so a recovery can answer one with the add-on off: Downloads' recovery refuses a magnet or `.torrent` out loud while every Downloads switch is off.

**Presentation** is the island's own API: `context.presenter` is `any IslandPresenting`, and add-ons post the Island value types (`IslandLevel`, `IslandNotice`, `IslandStatus`, `IslandMenuRow`, and `IslandPage` through `setPage`, with `watchPages` saying when its data is on show; notchcast/docs/island-shell.md "Presentation API" and "Pages"). `NotchcastCore` hands the controller `core.islandPresenter`, the island's own presenter, with no add-on stand-in between; what each call draws is the island's (island-shell.md).

**Doors** are the app's services an add-on reaches through `context`, one page each in [doors/](doors/). `NotchcastContext` and `NotchcastController` take them as one `services: NotchcastServices` value, which the controller passes through untouched; harnesses pass only the door they fake (`NotchcastServices(calendar: …)`) and the rest stay inert. A new door is three new files and two lines: `Core/Service/Notchcast<Door>.swift` (its type, inert default and `extension NotchcastContext` accessor), `Notchcast<Door>+Live.swift` beside `NotchcastCore.swift` (`init(core: AppCore)`), `doors/<door>.md`, one `var <door> = …` line in `Core/Service/NotchcastServices.swift` and one `<door> = …(core: core)` line in `NotchcastServices+Live.swift`. Both files merge by union (`.gitattributes`), so they hold one-line entries only.

A switch with none of commands, settings action, taps or a module has no user path and fails the registry harness (v1 shipped 35 such switches).

**Ownership.** There is one `NotchcastCore` instance, created by H1 inside `AppCore.start` and held by `AppCore`; it stops every module and removes the tap when the app terminates. Hook statics in upstream files are `@MainActor`, set once in `start`, and `nil` means stock behaviour. No second actor, no new `MainActor.assumeIsolated`.

**Debug scenes and probes** of an add-on live in its folder, so the delete test removes them. Nothing of an add-on goes into `IslandVerification` or any other shared scenes file.

## 3. Upstream hooks: the whole footprint of the add-on system

Only `v2/addons-core` touches upstream files, and only through these hooks. Each hook is a general injection point declared with stock types (a closure or static the core sets in `start`). No upstream file a harness compiles names a fork type. One upstream harness needs a fixture all the same: `Tests/AppInstallationTests.swift` stubs `HotKeyAction` and compiles `VisibilityStore.swift`, so its stub carries H4's case (+1); the dummy delete test found it.

| # | Upstream file | Hook | Lines |
| - | - | - | - |
| H1 | `App/AppCore.swift` | `NotchcastCore.start(self)` in `start()` | +1 |
| H2 | `Launcher/Model/CommandCatalog.swift` or `Launcher/Service/AppIndex.swift` | append add-on entries, filtered by `isEnabled` | +3 |
| H3 | `Launcher/UI/LauncherCoordinator.swift` | dispatch an add-on entry before stock dispatch | +1 |
| H4 | `HotKeys/Model/HotKeyAction.swift` (+`+EntryID.swift`, `Launcher/Service/VisibilityStore.swift`) | `case notchcastCommand(entryID:)`, its `defaultsKey` arm and entry mapping, and its place in `allowsHotKey`'s ungated list, so the stock Commands category never gates it (its switch does); stock `.command(CommandID)` cannot carry it without new `CommandID` cases | +6 |
| H5 | `HotKeys/Service/HotKeyManager.swift` | list, name, perform, register only while the owning switch is on | +5 |
| H6 | `Settings/SettingsTab.swift` | `case notchcast(NotchcastPane)` and its slug/title/icon arms; a `notchcast` sidebar section after Features listing `NotchcastPane.shown`; `allCases` derived from the sections, since the associated value rules out synthesis | +12 −2 |

H2 names the one file actually used once built. H4 and H6 add cases to upstream enums. Known cost: a future upstream exhaustive `switch` over `HotKeyAction` or `SettingsTab` breaks our build with no textual conflict; the sync rehearsal's ready-check is what catches it. Every upstream exhaustive switch that needed an arm is listed in this table and counts in the budget.

**Budget for `v2/addons-core` is a gate.** The numbers (files, +lines, −lines) live in one fork-owned file, `notchcast/addons-budget.env`; ready-check fails `v2/addons-core` above them. Raising the budget is a visible one-line change with the reason in the commit body. `notchcast/check-addons.py` runs in `ci-checks.sh` (so in ready-check and CI): core mode prints each upstream path with its +/− and fails above the budget; feature mode fails any path outside the branch's folders, its tests, its feature doc `notchcast/docs/features/<folder>.md` (case and hyphens ignored) and its `notchcast/licenses/borrowed/<Folder>.txt`; `--mode` (core, feature or none) or `--branch` is required, and `ci-checks.sh` passes the branch, which is core only for exactly `v2/addons-core` or `v2/addons-core-<n>` (the name a rebased core is pushed under since nothing force-pushes), feature for any other `v2/addons-*` and for any branch that adds an add-on or touches exactly one add-on's folder, none otherwise and always none for an empty name or a `train/*` one, whose diff merges several PRs (a branch over two existing add-ons also gets none, so it skips the folder check); on every branch a reference guard fails a fork-added line outside an add-on's folder that names its switch ids or slugs, or names one of its top-level types in code (strings, comments and nested types do not count; its registry line, other add-ons' `dependencies:` arrays and the core harnesses `Tests/nc-Notchcast-*.swift`, which pin the frozen ids, are exempt).

**Rule for feature branches:** `v2/addons-<name>` other than core touches zero paths that exist on upstream `main`. Allowed paths: `Tinycast/Features/Notchcast/<its folders>/**`, `Tests/nc-<its folders>-*.swift`, its feature doc `notchcast/docs/features/<folder>.md`, and `notchcast/licenses/borrowed/<its folder>.txt` with one `<Folder>: <file> ← <source> (<licence>)` line per file it borrows from (the file keeps its own notice; `NOTICE.md` points to `borrowed.md`, which points there). The gate derives this list from the folders whose add-on file gains its `// notchcast-addon-order:` line; nobody keeps a list of folders by hand. Anything else fails the gate. A feature that truly needs a new upstream hook stops and asks for a general hook in core.

## 4. Settings

A **Notchcast** section in the stock Settings sidebar, right after Features (H6), with one tab per `NotchcastPane`, in order: Island (`notchcast-island`), Agents (`notchcast-agents`), Keyboard & Mouse (`notchcast-keyboard-mouse`), Display & Sound (`notchcast-display-sound`, its Display & Sound and Music sections), Capture (`notchcast-capture`), Launcher Extras (`notchcast-launcher`), Downloads (`notchcast-downloads`), Power (`notchcast-power`), Notices (`notchcast-notices`) and Mac Tweaks (`notchcast-mac-tweaks`); each opens from `tinycast://settings/<slug>`. Island always shows and holds `NotchcastIslandSettingsRows`, the island shell's own rows ("Show in screenshots and videos", "Outline when open", "Open on hover" and "Position on displays without a notch", each found by search on the Island tab). An add-on tab shows only while a registered switch sits in one of its categories: `NotchcastCore` installs the registered categories into `NotchcastPane` before Settings can open, so a tab never reads `AppCore`. Each tab is a stock grouped `Form`, one section per category it holds: a switch row per feature, then while it is on one row per command with its alias and hotkey fields and its own "Show in launcher" checkbox (on by default, stored as `launcherHiddenCommands` in the `<bundle id>.notchcast` suite; off drops the command from the launcher, its hotkey still works), and its extra rows, empty categories hidden. Settings › Commands does not list add-on commands. Categories are a fixed, ordered list in Core (one line each); add-ons pick one, and nobody maintains a list of features. Adding a category is one line in Core plus the tab that holds it; moving a feature is one word in its descriptor. A later add-on whose category has no tab adds one `NotchcastPane` case with its categories, slug, title and symbol arms, all in Core; `SettingsTab` stays untouched.

Settings search finds every switch with no line in the add-on: core installs one search row per switch from the descriptors (title, subtitle, id, and the names and keywords of the switch's commands, which hide while it is off), and each category header is the anchor its rows scroll to, on its own tab; each shown tab gets one pane row. **Add-on switches have no `SettingsFileKey`**, a deliberate exception to the settings-file rule: a switch can grant a capability (an event tap, Accessibility-gated input), and a capability flag is never carried by `settings.json` or a backup, as with `snippetsEnabled`. They live only in the `<bundle id>.notchcast` suite. The launcher's own Hide on an add-on command turns that checkbox off (`NotchcastLauncherHides`), and stock hides an earlier version left on an add-on command are dropped at start, since no checkbox could undo them. Add-on command aliases, hotkeys and launcher checkboxes are not carried by `settings.json` either: its commands binding lists only `CommandID` cases (`LauncherSettingsFile.swift`), so they stay in this Mac's preferences.

Which add-ons a tab holds is in the README's generated list; an add-on PR never edits this table.

A category with no tab shows nowhere, so the first add-on in it lands together with its `NotchcastPane` case; the registry harness fails a switch that lands in no shown tab.

## 5. Proof

- **Delete test** `notchcast/check-addon-delete.py <Folder>|--rotate|--all`: in a scratch worktree, delete the folder, its `borrowed/<Folder>.txt` and `Tests/nc-<Folder>-*.swift`, regenerate the registry and the project, build Debug, run `Scripts/run-tests.sh`. It prints the step that failed and its log path; a tooling failure (load, timeout, xcodegen) is reported as a tooling failure, never as a contract breach. A surviving fork harness with neither a result nor a skip line in the run-tests log is a tooling failure; one the runner says it skipped (hosted-only off a hosted runner, `CI_SKIP_TESTS`, a runner skip) counts as skipped, and the PASS line names it. A READY for `v2/addons-<name>` runs it for each of its own folders and quotes the result. `ready-check.sh` runs `--rotate` (folder picked from HEAD's sha) after the build gates whenever the branch diff touches `Tinycast/Features/Notchcast/`, failing as `FAIL addon-delete`; other branches skip it and its extra Debug build. `--all` runs before every READY that changes Core, at one build per folder. A folder whose strings stay referenced elsewhere (`table: "Notchcast<Folder>"`), or a tree whose registry no longer generates without it, is a breach before any build. The scratch dir (`notchcast-delete.*` under `$NOTCHCAST_DELETE_SCRATCH` or the per-user temporary directory) holds `owner.pid`; SIGTERM, SIGINT or SIGHUP stops the running step's whole process group, removes the dir and exits 128+signal, and since SIGKILL skips that, every run first removes the dirs whose owner is dead and pid-less ones over an hour old. `--list` prints the folders at `--ref` and builds nothing. On CI, `gh workflow run delete-check.yml -f ref=<sha or branch>` runs the same check in one hosted `xcode-27` job (`.github/workflows/delete-check.yml`) that takes the folders in turn, about 15 minutes each: a failing folder never stops the rest, each prints its PASS/FAIL line, the logs are uploaded on failure, and the summary job lists folder → PASS, FAIL breach or FAIL tooling and fails if any folder did; `gh run view <id>` shows the table. The harnesses `CI_SKIP_TESTS` names are skipped there, as in every hosted run.
- **Reference guard** (every ready-check, all folders, no build): no file outside a folder names a top-level non-private type declared in it in code (strings and comments do not count), nor any of its switch ids, command slugs or entry ids as strings, except the registry line.
- **Shared-list guard** (`check-addons.py`, every branch, no build): fails a branch that edits the generated registry without changing `notchcast/addons.py`, adds an entry to `notchcast/licenses/borrowed.md`, adds anything between the README's `addon-tabs` markers but core text on a tab line (Island's) or a new empty tab line, or names a fork harness (`nc-*-test`, `notchcast-*-test`) on any line it adds to `config.env`; each message names the way through. `notchcast/addons-test.py` proves the generator on scratch trees and that the real tree generates.
- **Footprint gate** (stack lead's ready-check line): core within the budget file; feature branches zero upstream paths, allowed paths derived from the folders whose add-on file gains its order line.
- **Strings:** a build leaves upstream's `Localizable.xcstrings` byte-identical, and deleting a folder leaves no orphan string. With per-folder catalogs, a mechanical check fails on any add-on string that would be extracted into the stock table (a missed `table:`). If that check proves expensive, the fallback is plain English literals with no catalog (we ship English only); cost: no translation path later without touching every add-on.
- **Acceptance block** in every feature READY: (a) the user path proven by a live scene that does what the maintainer would do (press the key, see the result), not only a model harness; anything that cannot run here is NOT RUN and goes to the MBP; (b) "how to try it" in at most three plain lines for the maintainer; (c) which outside references it drew on (name, licence, what was taken). A feature the maintainer has not checked is "built, not accepted".
- **Registry harness** `Tests/nc-Notchcast-registry-test.swift`: ids and slugs unique and frozen: every switch id is either one of v1's raw values, all pinned in the harness bar the retired ones (`retiredIDs`), or declared `// notchcast-new-switch-ids:` in its own folder, exact match (a declared id that is pinned, retired or no switch of that folder has fails), and no id is declared by two folders, every switch has a user path, every category valid and in exactly one shown tab, dependencies name known ids or are reported as absent, and every add-on that declares `commands` has an icon harness of its own (below).
- **Icon harness** `Tests/nc-<Folder>-command-icons-test.swift`, one per add-on with commands: `// notchcast-kit: notchcast-command-icons`, `// notchcast-sources:` lines for the folder's descriptor and the Model and Service files it needs, stand-ins for its `live` systems and settings views, and `@main` calling `NotchcastCommandIconCheck.run(<Folder>Addon.self)` (`Tests/NotchcastCommandIconFixture.swift`): each command reaches the launcher index as a tile of its own real SF Symbol in its owner tab's tint, never the question mark. `Tests/nc-SmallCommands-command-icons-test.swift` is the shortest to copy.
- **Core harness** `Tests/nc-Notchcast-core-test.swift`: preferences on a scratch suite, module start/stop on toggle, tap order through the controller, hotkey key strings, presentation-seam recording, the tab → category map, which tabs show, unique slugs and their deep links, nc command entries owned by their add-on tab, and each switch drawing its commands' alias and hotkey fields. **Tap harness** `Tests/nc-Notchcast-tap-test.swift`: fake tap hub installed only while subscribed, resets, stale activations, liveness and the trust monitor. Both share `Tests/NotchcastTapFixtures.swift`. **Visibility harness** `Tests/nc-Notchcast-visibility-test.swift`: the stock Commands category never hides an add-on command or blocks its hotkey, against the real `VisibilityStore` and a stub `AppEntry`. **Alias harness** `Tests/nc-Notchcast-command-alias-test.swift`: shipped commands take an alias and a hotkey, stay reachable with Commands off, and their "Show in launcher" checkbox alone decides whether the launcher finds them by name and alias. **App proof** `addon-launcher` (`notchcast/app-proof.py`): the shipped wiring finds the first registered command needing no dependency or grant by name and alias over an earlier version's stock hide, and its checkbox off drops it on the same turn.
